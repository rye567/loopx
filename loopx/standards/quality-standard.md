# 质量标准

## 目的

定义客观检查，在进入下一阶段前拦截薄弱或不完整的智能体输出。

## 检查结果契约

每个检查只能返回以下状态之一：

- `PASS`
- `CHANGES_REQUIRED`
- `BLOCKED`
- `SKIPPED`
- `ACCEPTED_RISK`

每个非 `PASS` 结果必须包含：

```yaml
return_to: ""
blocking_issues: []
required_actions: []
evidence: []
user_confirmation_required: false
```

v2 对风险接受使用更窄的范围：普通阶段不能直接用阶段级 `ACCEPTED_RISK` 代替必需规则；必须在 `quality_result.rule_results` 中标明具体规则，并在 `accepted_risks` 中提供相同规则 ID、具体理由和项目内真实确认文件。整体执行等级降级确认只适用于等级选择，不能替代逐规则确认。阶段结果结构继续保留 `ACCEPTED_RISK`，用于 v1 兼容和等级选择记录。

## 核心检查

- 所选执行深度要求的产物存在。
- 工作清单中的工作项已解决或被明确阻塞。
- 阶段结果包含合法状态、返回目标、下一步动作和证据。
- 实际 Git 差异与批准的写入范围一致。
- 测试证据能映射回验收标准。
- 测试创建的数据已完成清理验证。
- CI 或远端验证缺口已声明。
- 规则快照中的适用必需规则均有结构化结果和有效证据。
- 安全或性能风险对应的专属结果存在，未执行项准确归类。
- 规则快照摘要与运行状态一致。

## 项目负责的质量指标

LoopX 不提供通用的文件行数、方法行数、覆盖率或复杂度通过值。项目如需检查这些指标，必须在项目策略中明确给出指标、数值、来源和适用范围；未配置时不参与通过判断。

- 大文件和大方法仍应在审查中结合职责与可读性判断，但不能把统一行数当作跨项目结论。
- 项目可以声明更严格的静态检查命令，命令结果必须记录来源和证据。
- 不提交 debug print、临时 sleep 或测试后门。
- 不硬编码密钥、token、租户 id、密码或生产端点。
- 未经过设计批准，不做大范围依赖新增。

## 通过标准

质量检查只有在必需检查都有硬证据时才能通过。结构化结果使用 `quality-result.schema.json`；按风险补充 `security-result.schema.json` 或 `performance-result.schema.json`。LLM 审核文字本身不是充分证明。

## 失败 / 返回规则

- 需求缺口：返回需求阶段或阻塞等待澄清。
- 设计缺口：返回方案设计。
- 测试设计缺口：返回测试设计。
- 实现缺口：返回开发。
- 验证缺口：返回测试执行或健康检查。
